# 効果的な使い方・設定

## プロンプトの書き方

**具体的に書く**

```
# 悪い
> バグを直して

# 良い
> src/api/users.tsの42行目でTypeErrorが発生します。
> "Cannot read property 'id' of undefined" というエラーです。
> userがnullのケースを考慮して修正してください。
```

**コンテキストを与える**

```
> このプロジェクトはNext.js 14 + TypeScript + Prismaで構成されています。
> 認証にNextAuthを使っています。
> パスワードリセット機能を追加してください。
```

**制約を明示する**

```
> テストは変更しないでください。実装側だけ直してください。
> 一度にすべて変更せず、まず方針を説明してから実装してください。
```

**大きなタスクは分割する**

```
# Step 1: 方針確認
> 決済機能を追加したいです。どんなファイルを作る必要があるか教えてください。

# Step 2: 実装
> では、まずStripeのWebhookハンドラーから実装してください。
```

## CLAUDE.md — プロジェクトルールの設定

プロジェクトルートに置くと起動時に自動で読み込まれる。毎回同じ指示を書かなくて済む。

**`/init` で自動生成する（推奨）**

```bash
> /init
```

プロジェクトを自動解析して CLAUDE.md の初期テンプレートを生成してくれる。手動で一から書くより、既存コードベースの構成・使用技術に合った内容が得られる。生成後に不要な項目を削除したり、チーム固有のルールを追記するだけでよい。

**手動で書く場合の例:**

```markdown
# プロジェクトについて

ECサイトのバックエンドAPI。Node.js 20 + TypeScript + Express + PostgreSQL (Prisma)。

## コーディングルール

- 関数は必ず型注釈を書く
- async/awaitを使う（Promiseチェーンは使わない）
- エラーハンドリングはResult型パターン（src/types/result.ts参照）
- テストはVitest + MSWで書く

## よく使うコマンド

- `npm run dev` — 開発サーバー起動
- `npm test` — テスト実行
- `npm run lint` — Lint実行

## 注意事項

- 本番DBには直接繋がない
- APIキーは.envから取得（ハードコード禁止）
```

サブディレクトリに置くこともできる:

```
your-project/
  CLAUDE.md          # プロジェクト全体のルール
  src/
    CLAUDE.md        # srcディレクトリ固有のルール（任意）
```

### 効果的な CLAUDE.md の書き方

**プロジェクト固有の情報に絞る**

どのプロジェクトでも同じルール（コーディングスタイル、コミット形式など）は `~/.claude/rules/` に書く。CLAUDE.md はこのプロジェクトだけに必要な情報を書く場所。

```markdown
# CLAUDE.md に書くべきもの
- 技術スタックとバージョン（Next.js 14 + Prisma 5.x）
- ディレクトリ構成の概要
- よく使うコマンド
- プロジェクト固有のルール（エラーハンドリングの方式など）
- 地雷情報（本番DBには繋がない、など）

# ~/.claude/rules/ に書くもの（CLAUDE.md に書かない）
- コーディングスタイル全般
- コミットメッセージのフォーマット
- テストカバレッジの基準
```

**「どこを見ればわかるか」を書く**

実装パターンやアーキテクチャの詳細を全部書くより、参照先を示すほうが効果的。

```markdown
## アーキテクチャ

- APIルート: `src/app/api/` 以下（App Router）
- DBアクセス: Prisma経由のみ（生SQLは禁止）
- 認証: `src/lib/auth.ts` を参照
- エラーハンドリング: `src/types/result.ts` の Result 型パターンを使う
```

**禁止事項は理由とセットで書く**

理由がないと、Claudeが例外ケースを判断できない。

```markdown
# 悪い例
- any を使わない
- 直接DBに繋がない

# 良い例
- `any` は使わない（型安全性が失われ、バグの温床になるため）
- 本番DBに直接繋がない（開発中の誤操作で本番データを破壊するリスクがある）
  → ローカルでは docker-compose up で起動したDBを使う
```

**コマンドは実際に動くものだけ書く**

古くなったコマンドはむしろ混乱の原因になる。最低限でよい。

```markdown
## よく使うコマンド

- `npm run dev` — 開発サーバー起動（http://localhost:3000）
- `npm test` — ユニットテスト実行
- `npm run db:migrate` — DBマイグレーション適用
```

## ~/.claude/rules/ — 全プロジェクト共通ルール

`~/.claude/rules/` に Markdown ファイルを置くと、**すべてのプロジェクトで自動的に読み込まれる**。

| | CLAUDE.md | ~/.claude/rules/ |
|---|---|---|
| スコープ | そのプロジェクトのみ | 全プロジェクト共通 |
| 用途 | プロジェクト固有のルール | 自分のコーディングスタイル・習慣 |
| Gitで管理 | する（チームと共有） | しない（個人設定） |

### ファイルの作り方

普通の Markdown ファイルを置くだけ。特別な書式は不要。

```bash
mkdir -p ~/.claude/rules
```

```markdown
# ~/.claude/rules/coding-style.md

## 命名規則
- 変数・関数: camelCase
- 定数: SCREAMING_SNAKE_CASE
- コンポーネント: PascalCase

## 禁止事項
- console.log を残さない
- any 型を使わない（型アサーションも原則禁止）
```

### カテゴリ別に分割する

1つのファイルにまとめるより、テーマ別に分割するほうが管理しやすい。

```
~/.claude/rules/
  coding-style.md    # コーディングスタイル
  git-workflow.md    # コミットメッセージ・PRの作り方
  agents.md          # エージェントをいつ使うかのルール
  verification.md    # テスト・検証の基準
```

### 効果的なルールの書き方

**「何をするか」より「なぜするか」を書く**

```markdown
# 悪い例
- オブジェクトをミューテートしない

# 良い例
## イミュータビリティ（重要）
常に新しいオブジェクトを作成する。ミューテートすると
副作用が追いにくくなりデバッグに時間がかかるため。

// 悪い例
user.name = name

// 良い例
return { ...user, name }
```

**トリガー条件を明示する**

Claudeがいつそのルールを適用すべきか書いておくと精度が上がる。

```markdown
## コミット前チェック（コミット操作のたびに必ず確認）
- [ ] ハードコードされたシークレットがない
- [ ] console.log が残っていない

## セキュリティ問題を見つけたとき（即座に停止して対処）
1. 作業を止める
2. security-reviewer エージェントを呼ぶ
3. 修正してから次に進む
```

**CLAUDE.md との使い分け**

```
CLAUDE.md に書くもの:
- このプロジェクトの技術スタック（Next.js 14 + Prismaなど）
- よく使うコマンド（npm run dev など）
- プロジェクト固有の注意事項

~/.claude/rules/ に書くもの:
- 自分のコーディングスタイル（どのプロジェクトでも同じ）
- コミットメッセージのフォーマット
- エージェントの使い方の好み
```

## よく使う設定

### 設定ファイル

設定は JSON ファイルで管理する。スコープが3段階あり、後から読まれるものが優先される。

| ファイル                      | スコープ             | 用途                              |
| ----------------------------- | -------------------- | --------------------------------- |
| `~/.claude/settings.json`     | グローバル           | 全プロジェクト共通の個人設定      |
| `.claude/settings.json`       | プロジェクト         | チーム共有設定（コミット対象）    |
| `.claude/settings.local.json` | プロジェクトローカル | 個人用の上書き（.gitignore 推奨） |

**基本的な設定は `/config` で変更する（推奨）**

セッション中に `/config` を実行するとインタラクティブなメニューが開く。変更内容は自動で `~/.claude/settings.json` に保存される。

```
/config
```

`/config` で変更できる主な設定:

| 設定           | 内容                              |
| -------------- | --------------------------------- |
| モデル         | opus / sonnet / haiku の切り替え  |
| 努力レベル     | low / medium / high（推論の深さ） |
| テーマ         | ターミナルの表示テーマ            |
| エディタモード | Vim モードの有効/無効             |
| 言語           | UI・応答言語                      |
| Output style   | Claudeの応答スタイル（後述）      |

#### Output style

Claudeの応答形式を切り替える機能。ビルトインスタイルが3種類用意されている。

| スタイル      | 特徴                                                                        |
| ------------- | --------------------------------------------------------------------------- |
| `Default`     | 標準のコーディング向けスタイル                                              |
| `Explanatory` | 実装の要所に Insight を挿入して教育的に説明する                             |
| `Learning`    | Claudeが `TODO(human)` を残し、実装の一部をユーザーに委ねる対話型学習モード |

## /branch — 会話を分岐して複数のアプローチを探索する

同じ起点から複数の実装方針を試したいときに使う。`/branch` で現在の会話を分岐し、各分岐で独立したアプローチを探索できる。

```
> OAuthで認証を実装してください

# ここで2つの方針を比較したくなった
/branch

# 分岐A: このままOAuth2 + JWTで進める
# 分岐B: セッションベース認証で試してみる
```

- 分岐後の各会話は独立しており、互いに影響しない
- 分岐はセッション終了後も保持される（`/resume` で再開可能）
- コードは共有される（会話レベルの分岐。ファイルシステムの分離は `--worktree` オプションを使う）

**`/fork` との関係**: v2.1.77 で `/fork` から `/branch` にリネームされた。`/fork` も引き続き動作する。

**使い分け**:

| 目的 | 方法 |
|------|------|
| 同じコードベースで複数アプローチを試す | `/branch` |
| 完全に独立した環境で並列作業 | `claude --worktree` |
| 途中まで戻って別の方向で進み直す | `/rewind` |

## トラブルシューティング

**的外れな回答が続く** → `/clear` でリセットして指示し直す

**会話が長くなって遅い** → `/compact` で要約するか `/clear` でリセット

**変更を取り消したい** → `git checkout -- <file>` か「さっきの変更を元に戻してください」と頼む

**意図しないファイルを変更された** → `autoApprove: false`（デフォルト）にしておけば変更前に確認が入る
